Build machines

How do I make a Windows VM with Chocolatey packages already installed?

This example builds win-tools01 with 7-Zip and Git. You’ll need a Windows Server installer, a VirtIO guest-tools ISO on the node, and guest network access to Chocolatey and the package download sites.

  1. Open Create machine. Choose Virtual machine, then Windows Server. Enter the machine name. Under Guest login, use your Windows build default or enter a separate Administrator password.
  2. Choose Windows ISO if the wizard offers a source choice. Select the ISO and a Windows edition. Choose an edition with Desktop Experience if you want a graphical desktop. Check the destination node and storage, then select Continue.
  3. In Software & scripts → Packages, tick Set up Chocolatey. Enter 7zip, git in Packages to install. Use Browse Chocolatey packages to look up other package IDs.
  4. Choose Review build. Check the edition, destination and package list, confirm the build and choose Create 1 machine. You can leave the wizard and follow the job in Activity.

Check the result. To reuse the same login on future machines, open Credentials and choose a Windows or Linux default under Defaults for new machines. After the job succeeds, sign in to the guest and run choco list to see the installed packages. To reuse the unattended setup elsewhere, open the ISO build’s job and choose Download reusable answer file. That archive uses placeholders for credentials.

How do I make a reusable Windows template and clone it?

  1. In Create machine, select Reusable template before choosing Windows Server. Give the base a name such as win-base. Pick the Windows ISO, edition and setup login.
  2. Add the software every clone should inherit. For example, install 7-Zip in the base and leave machine-specific roles, such as domain promotion, for deployment. Review and approve Create 1 template.
  3. Wait for the job to succeed. Proxmate installs the software, runs Sysprep, shuts down the base and converts it to a Proxmox template. The clone goes through Windows first-boot setup.
  4. Open Inventory, select Templates → Clone template on win-base, and choose Full copy (independent VM) for a guest with its own disks. Enter a fresh name such as win-dev01 and choose the Administrator login. Add any clone-specific scripts, review and create.

Check the result. Inventory should list the base under Templates and the new guest under Running after setup. Run hostname inside the clone and check that your base software is present.

How do I build a Linux VM I can SSH into straight away?

  1. Open Create machine and select Virtual machine → Ubuntu. For a 24.04 guest, choose an Ubuntu Server 24.04 LTS amd64 live-server ISO. The guided ISO installer also supports Ubuntu Server 22.04 and 26.04 LTS.
  2. Name the VM devbox01. In Guest login, use the Linux build default or choose a separate SSH key and username. Enter your GitHub username to import its public SSH keys, or paste your workstation’s public key. Keep the corresponding private key on your workstation. Password sign-in is optional for a working VM.
  3. In Software & scripts → Packages, enter curl, git. Leave firewall and update settings at their Ubuntu defaults unless you want a specific change. Review and create the machine.

Check the result. On success, use Copy SSH command from the notification or machine page. Run it on the workstation holding your key, then try git --version.

Other installers. Choose Debian for Debian 13 amd64 netinst or DVD-1, or Rocky Linux for Rocky 10 x86_64 Boot, Minimal or DVD. Supply packages from that distribution. Give network installers guest DNS and access to their package mirrors.

How do I find out which installer ISOs I can use?

  1. Open ISO library and choose the Proxmox server where you plan to build. Proxmox calls each server a node. The list shows files in the Proxmate ISO folder and ISO storage available to that server. A Candidate is a filename match.
  2. Choose Check media on a file to inspect it, or Check installers to check one candidate for each unverified OS family. If prompted, configure verified Proxmox SSH in Server settings. For Windows, select the VirtIO guest-tools ISO too.
  3. Look for Verified and, for Windows, inspect the reported editions. Choose Use in Create to carry that file and server into the wizard. A guided build copies the installer when needed.

To copy a file ahead of time, choose Copy to Proxmox storage… beside a file in the Proxmate ISO folder. Pick the destination ISO storage on your server and choose Copy ISO. The original stays in the folder.

Two storage choices. The installer ISO is what the guest boots. Setup media storage is where Proxmate writes the extra media containing this VM’s unattended installation settings. The VM’s system disk has its own storage choice.

Run scripts

How do I run an Ansible script on an existing Windows or Linux VM?

  1. Open Run scripts, select one or more running guests of the same platform, then choose Choose scripts. For one machine you can also choose Run script on its Inventory row.
  2. Pick a Library script. On Windows, add Create a tools folder and change Folder name from LabTools to OpsTools. On Linux, try Create a shared tools directory. Add steps in the order you want them to run.
  3. Proxmate uses each VM’s saved guest login. When a login is missing, select a compatible credential or supply one. Windows needs working WinRM and a login with the required privileges. Linux needs SSH and sudo access for system changes.
  4. Choose Review run. Check the machine names, addresses, script order and inputs, then approve the run. Activity records a result for each target.

Check the result. On Windows, Test-Path C:\OpsTools should return True. On Linux, ls -ld /opt/lab-tools should show the directory. For a single-use task, choose One-off script → Ansible YAML, paste a guest task list and review the targets.

How do I turn a useful task into a script everyone can reuse?

  1. Open Script library. Find Create a tools folder and choose Save a copy. Give it a descriptive name such as Create a project folder.
  2. Keep the input variable name, change its display label to Project folder and give it a default such as Projects. The module argument C:\{{ proxmate_inputs.name }} uses the value supplied for each run.
  3. Choose Check syntax, then Save copy. Open the saved script’s Run script action to try it on one VM. Choose Use in lab to add it to a lab definition.

When to save a copy. A saved script can be selected during a build, added to a lab or run later against existing machines. For guest PowerShell or Linux shell, start with a matching starter in the library. PowerShell on Linux requires pwsh on the guest.

Recreate labs

How do I make a lab I can recreate or share?

For example, define an Ubuntu web server and a separate client once. A lab pack records their roles, dependencies, software steps and custom script source.

  1. In Labs, choose Create lab → Add role → New machine. Add an Ubuntu role named web01. Under Role settings choose the install source. Under Process, add Install a Linux package with nginx, followed by Manage a Linux service with service nginx and state started.
  2. Add an Ubuntu client01 role with the package curl. In the client’s Role settings → Starts after, select web01. The client waits for the server’s build and steps to succeed.
  3. Choose Save lab to keep the definition. From Saved packs, choose Set up lab when ready. Map each role to the destination’s media, node, storage and network. Supply logins, Review lab, inspect both roles and confirm Deploy lab.
  4. Follow each role in Deployments. On the client, run curl http://WEB_IP/ using the server address from Inventory. With network access between the guests, you should see the nginx welcome page.

Recreate it elsewhere. Choose Download ZIP on the saved pack, then Labs → Import ZIP on the receiving dashboard. Bundled custom scripts travel with the pack. The receiving dashboard supplies the referenced built-ins, installation media or templates and fresh credentials. Check custom scripts for embedded secrets before sharing.

Start with what you have. Saved build reuses a reviewed build. VM blueprint copies settings for a new machine. Existing VM runs the role’s steps on the actual guest you select during deployment, with a separate confirmation.

Try a smaller pack first. In Labs → Import ZIP, choose Download example pack. It defines one Ubuntu cloud VM with curl and a bundled directory-creation task. Import the ZIP and inspect the roles and steps before choosing whether to deploy.

How do I build a Windows domain controller and join a member server?

This example creates a new forest, lab.example.test, with two Windows Server guests on the same lab network. Proxmate automates promotion and stages a join script on the member. An administrator enters a delegated join credential on the member to finish.

  1. Give the controller a stable address, for example through a DHCP reservation. Configure the member to use the controller for DNS through the lab’s DHCP settings or its network adapter before the join. Use an isolated network when running a second copy of the same forest.
  2. In Script library, choose New script. Name it Prepare member domain join, select Windows and Ansible YAML, and paste the task below. Choose Add input with variable domain, label Forest DNS name and default lab.example.test. Check syntax and save.
Show the Ansible task for the member server 
- name: Put the domain join script on the public desktop
  ansible.windows.win_copy:
    dest: 'C:\Users\Public\Desktop\Join-LabDomain.ps1'
    content: |
      $ErrorActionPreference = 'Stop'
      $domain = '{{ proxmate_inputs.domain }}'
      $computer = Get-CimInstance Win32_ComputerSystem
      if ($computer.PartOfDomain) {
        throw "This server already belongs to $($computer.Domain)."
      }
      Resolve-DnsName -Type SRV "_ldap._tcp.dc._msdcs.$domain" | Out-Null
      Add-Computer -DomainName $domain -Credential (Get-Credential) -Restart
  1. In Labs → Create lab, add a New machine named dc01. Choose Windows Server with Desktop Experience. Add Set up a Windows domain controller under Process. Enter the forest DNS name. Use the built-in Administrator login for promotion and supply a separate Directory Services Restore Mode password at deployment.
  2. Add a second new Windows Server role named member01, also with Desktop Experience. Add Prepare member domain join to its Process with the same forest name. In the member’s Role settings → Starts after, select dc01. Save, set up and review the lab, then deploy it.
  3. After both roles succeed, sign in to member01 as a local administrator. In elevated Windows PowerShell run & "$env:PUBLIC\Desktop\Join-LabDomain.ps1". At the prompt enter a domain account allowed to join machines. The script checks domain DNS discovery, joins the computer and restarts it. The credential stays out of the saved pack.

Verify both guests. On the restarted member, Test-ComputerSecureChannel should return True. On dc01, open Active Directory Users and Computers from the public desktop and find the member’s computer account. Group Policy Management is on the same desktop. Microsoft’s Add-Computer reference

Maintain machines

How do I recover when a guest changes address or a script fails?

  1. Open the failed job in Activity and identify the affected VM and step. If the address changed, choose Refresh connection in the job when offered, or on the VM’s Inventory row.
  2. Check the addresses reported by the QEMU Guest Agent. Select the current guest address and matching guest login, then choose Test and save. If Windows is newly imported, open its machine page and choose Check WinRM setup to inspect the listener. Use Open console if remote access needs repair.
  3. Reopen the failed job. When Review remaining tasks is offered, check which steps completed and whether the failed step partly changed the guest. Confirm the remaining steps. Otherwise start a fresh Run scripts review for just the affected VM and outstanding steps.

Check the result. Look for a successful login test and a new successful job for the right guest. A reachable port alone does not verify its identity or login.

How do I test that a backup boots without touching the original VM?

  1. Open More tools → Backup recovery. Pick the archive by node and original VM ID, then choose Restore / test.
  2. Enter an unused destination VM ID, a distinct name such as restore-test and storage with room for the copy. Keep its network interfaces disconnected. Select the boot test if the backed-up guest has a working QEMU Guest Agent.
  3. Choose Review restore, check the archive and destination, and confirm. Follow the job in Activity.

What a pass proves. The restored copy booted and answered through the guest agent. Proxmate shuts it down and retains it. Check application data separately, then account for the retained copy and its disk space.

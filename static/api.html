Proxmate API

The dashboard and your scripts use the same API. Configuration is saved immediately. Infrastructure operations run as durable background jobs.

Download OpenAPI 3.0 specification · Import this into Postman or your preferred API client.

Windows provisioning guide for AI agents · Discover media, review a custom build and follow it through to completion.

Authentication

Use Authorization: Bearer TOKEN. The token is generated on first launch in /data/api-token inside the container. Retrieve it locally with docker compose exec proxmate cat /data/api-token. Treat it as an administrator credential. Rotate it by replacing that file and restarting the service.

Select your server (0.5)

GET /api/server returns the saved server ID and connection metadata; it never returns the password. POST /api/server/test checks HTTPS API login and nodes only, without saving or running SSH. POST /api/server/connect tests and saves; POST /api/server/disconnect disables operations without changing VMs. Include expected_id (null for first setup). Connection fields are url, username, password, verify_tls, ssh_user and ssh_fingerprint. A blank password retains the saved value only for the same address and user. Set replace_confirmed=true to archive the previous host settings and plans. Changes require an idle queue and disabled schedules/policies.

Set PROXMATE_SERVER_ID to the id returned by GET /api/server. Include X-Proxmate-Server on host-bound POSTs: jobs, management except credentials/tasks, and lifecycle plan/run/families/policies. A stale or missing ID returns 409. Reload and review targets before retrying; use a new idempotency key after replacing the server.

Read your lab

curl -H "Authorization: Bearer $PROXMATE_TOKEN" http://localhost:8088/api/state

Queue an operation

curl http://localhost:8088/api/jobs \
  -H "Authorization: Bearer $PROXMATE_TOKEN" \
  -H "X-Proxmate-Server: $PROXMATE_SERVER_ID" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: ubuntu-template-9000" \
  -d '{"action":"linux-template","node":"pve","vmid":9000,"name":"ubuntu-template","storage":"local-lvm","bridge":"vmbr0"}'

A 202 response contains id and url. Poll that URL. Only succeeded confirms completion. A failed or interrupted job may have left resources behind; inspect them before retrying. Reuse the same idempotency key and payload to retrieve the original job without rerunning it.

Guided Windows and Linux builds (0.6)

GET /api/simple/options discovers resources and media. POST /api/simple/editions reads named editions from node and source (Proxmox ISO volume ID or library:filename.iso). POST /api/simple/plan takes os, name, count, purpose, selected tasks, Windows source/edition/password or Ubuntu profile/username. Advanced resource overrides are optional. The response lists exact machines and software without secrets. POST /api/simple/run takes plan_id, confirmed=true and risk_confirmed when requested; it returns one idempotent job per machine. Jobs create, bootstrap, authenticate and apply software, then optionally generalize into a template. Real installation can require console attention. POST /api/simple/existing-plan reviews Operations scripts against existing VMs. Supply targets and either ordered tasks with named parameters or one_off with platform, kind, body and optional Ansible parameters and params. Each VM uses its saved login. Supply credential_id or credential only for missing connections. Review checks the script and saves any newly discovered connections. Submit the reviewed plan to /api/manage/run. All POSTs require X-Proxmate-Server.

Build credential defaults

GET /api/manage/credentials/defaults returns the Windows and Linux defaults, each null or an object containing id, name and username. POST to the same endpoint with platform and credential_id (null to clear). GET /api/simple/options includes the same map under build_defaults. Send the chosen build_credential_id in a guided review or a repeated build, or in secrets for each new lab role. Omit it for a separate guest login. Review build_login and check the completed guest connection. Shared Windows passwords are excluded from answer-file downloads.

Advanced provisioning wizard

GET /api/catalog lists supported profiles and Windows options. POST /api/provision/plan validates a provision payload without contacting Proxmox and returns steps plus a redacted XML preview. Submit the same payload to POST /api/jobs with action: provision and confirmed: true to build it. POST /api/windows/answer-file explicitly downloads XML, which can contain the supplied password.

Guest management

GET/POST /api/manage/{kind} lists or saves credentials, connections, tasks, groups, recipes and schedules. Omit id to create; supply an existing id to update. Connections are keyed by node and vmid. Credential secrets are encrypted and write-only; blank secret fields retain existing values. Delete unreferenced records with POST /api/manage/{kind}/{id}/delete and an empty JSON object.

For Rocky Linux 10 x86_64, discover DVD, Minimal and Boot ISOs under destinations[].rocky_isos. Review os: rocky with a name, optional SSH keys, working-VM password and Linux tasks. Omit the source to select the newest release, preferring DVD, then Minimal, then Boot. Minimal and Boot require guest access to the matching online Rocky repositories. Use rocky_templates for clones. ISO jobs offer GET /api/jobs/{job_id}/kickstart.

For Debian 13 amd64, select an installer from destinations[].debian_isos or omit the source to use the newest discovered version. Review os: debian with a name, optional GitHub or pasted SSH keys, linux_password on working machines, and Linux tasks. A successful template appears under debian_templates. Clone with template_id and source_kind: template. Download the reusable preseed at GET /api/jobs/{job_id}/preseed.

For Ubuntu Server 22.04, 24.04 and 26.04 LTS amd64 ISO autoinstall, discover each destination’s ubuntu_isos with GET /api/simple/options. Review with os: ubuntu, source_kind: iso and the exact source ID. The ISO supplies the release. Choose an optional ubuntu_install_source from ubuntu.install_sources for Standard (default) or Minimized. ISO builds use the Proxmox defaults for firmware, machine type and display. Optional inputs include github_username, ssh_public_key, ubuntu_firewall, ubuntu_updates and Linux tasks. The review gives workstation key fingerprints and confirmation requirements. Jobs with has_autoinstall offer reusable installer YAML at GET /api/jobs/{job_id}/autoinstall.

For a completed VM job with remote_kind, send its node, vmid and job_id to POST /api/simple/machine/remote-access. A machine discovery identity can also identify the target. The response provides a current RDP host/port or SSH command. An unavailable RDP listener returns a null kind. Send the selected server header on the remote access request.

Guided working Ubuntu VMs and clones accept ubuntu_password in the build review request. If supplied, the job enables console and SSH password sign-in for the selected account after software finishes. The review reports password_login. Keep the password in the operator's secret store and omit it for reusable templates.

Library scripts declare optional input_types per parameter. Text is the default. Choice inputs specify a list of choices, boolean inputs accept the strings true and false, and Windows drive inputs accept unused letters D through Z. Use POST /api/simple/drive-letters with targets to read the union of occupied letters before review. Reviewed inputs are checked again when a drive task runs.

For a failed script or readiness check with a changed guest address, GET /api/jobs/{job_id} can return connection_recovery. Match its server ID and send a returned target to POST /api/simple/machine to check the reviewed VM and read its current addresses. The dashboard provides Refresh connection in the failed job and on the Machines list. Use Test and save before reviewing a new run for that VM.

Machine discovery returns suggested_credential_id. For a reused Windows VM ID it can identify the current build’s login. Send the selected login, current guest IP, platform, identity and connection revision to POST /api/simple/machine/connect. For Proxmate-prepared Windows guests the dashboard can verify a changed listener through the guest agent over verified Proxmox HTTPS or pinned SSH. A successful response includes verified_at.

First configure a guest credential and connection. Windows uses HTTPS WinRM and NTLM; Linux requires a verified SHA256 SSH fingerprint. Custom scripts are trusted administrator code. Saved Ansible scripts are restricted task lists, not whole playbooks. Guest task output is withheld to protect secrets.

Review an operation with POST /api/manage/plan:

{"operation":"tasks","targets":[{"node":"pve","vmid":201}],
 "tasks":[{"id":"install-chocolatey","params":{}},
          {"id":"chocolatey-package","params":{"package":"7zip"}}],
 "snapshot_before":true}

The response contains a plan ID, exact targets, task order, settings and a dangerous flag. Plans expire after 30 minutes. Send POST /api/manage/run:

{"plan_id":"RETURNED_ID","confirmed":true,"risk_confirmed":false}

Dangerous operations/scripts require risk_confirmed=true. Repeating a plan ID returns the same job. Changes to groups or scripts cannot expand a reviewed plan. Credential rotation and VM identity/disk changes invalidate execution; review again. Poll the returned job URL for per-VM results.

Management operations: tasks, readiness, start, shutdown, stop, resize, backup, snapshot and restore. Resize requires cores and memory (MB); backup requires backup_storage; restore requires snapshot. Resize/restore require stopped VMs. Shutdown never falls back to force-stop. GET /api/manage/snapshots/{node}/{vmid} lists snapshots. Storage support is required; failed pre-task snapshots abort that VM's tasks.

Repeat a guided build

GET /api/simple/recipes lists named builds. POST to the same path with a name and exactly one guided plan_id or job_id to save a shortcut. Use POST /api/simple/recipes/{id}/delete with an empty object to remove it. Job details expose reusable_build when a guided job has reusable settings.

POST /api/simple/plan with a new name and reuse: {"recipe_id":"…"} or reuse: {"job_id":"…"}. Count defaults to one. Supply a Windows build credential or fresh Administrator password. For Linux, supply a fresh guest password when password_login is true. Confirm generalized for Windows template sources. If needs_key_source is true on a historical Ubuntu build, supply github_username or ssh_public_key again. Review rechecks placement, source and current library scripts. Confirm the resulting plan through /api/simple/run.

Recover guest software

Failed or interrupted job details can include task_recovery with a server_id and targets. Follow a target's successor when present. POST /api/simple/recovery/plan with the original job_id and the target string to review the remaining frozen tasks on that VM. The review flags a previously started task, any requested snapshot and final template preparation. Confirm through /api/manage/run and poll the new job. Its recovery_of field links to the preceding run.

Bootstrap, backup recovery and template versions (0.4)

Provisioning accepts an optional bootstrap object. Linux cloud images require snippet_storage and use cloud-init vendor data, preserving generated users/networking. Windows requires management_cidr and a trusted agent_iso. It configures HTTPS WinRM first and retries guest-tool installation. New builds pin agent_sha256 from the selected ISO; unsigned MSI installers require this matching checksum, while Windows enforces driver signatures. verify=true requires start=true, VM purpose and a matching credential_id. Public SSH/TLS identity is retrieved through the authenticated Proxmox guest-agent API before verifying guest authentication and saving a connection. The provisioning plan includes a bootstrap_preview. POST /api/bootstrap/helper downloads a script without executing it.

GET /api/lifecycle/state returns families, versions, builds, backup policies and successful copy reports. POST /api/lifecycle/families with a name creates a family.

POST /api/lifecycle/plan accepts these operations:

OperationSettings and behavior
backup-restorenode, unused vmid, storage, name and archive. No overwrite, unique identity, disabled onboot and no immediate start. disconnected defaults true. Optional boot_test requires disconnected networking; timeout is 30-1800 seconds. Copies are retained.
backup-retentionnode, backup_storage, source_vmid, keep and older_than_days. Returns exact deletion candidates. Protected/newest archives are retained and eligibility checked again before deletion.
version-buildfamily_id, recipe_id, vmid, name, label; optional start. Windows requires fresh accept_eula/wipe_disk confirmation and optional write-only admin_password. Frozen recipe tasks run only after verified bootstrap; otherwise remain planned.
version-registerfamily_id, node, vmid, label and prepared=true. Requires a generalized stopped guest without generated answer media. Converts to template if needed and disables onboot. Provenance excludes setup passwords.
template-testversion_id, node, unused vmid, storage and name. Full disconnected clone, guest-agent boot check and graceful shutdown. No force-stop/deletion. Evidence is tied to unchanged template configuration.

version-cloneversion_id, node, unused vmid, storage and name. Checks registered identity before full cloning. Remains stopped unless an explicitly requested disconnected test is performed.

POST /api/lifecycle/run with plan_id and confirmed=true queues the reviewed plan once. Archive deletion/custom scripts also require risk_confirmed=true. Plans expire after 30 minutes. Repeating the ID returns the same job. Poll /api/jobs/{id} for the actual result.

POST /api/lifecycle/policies saves mode=restore-check or retention, scoped to node/backup_storage/source_vmid. Policies default disabled. Restore checks require destination storage and range_start/range_end (at most 1000 IDs); each latest-backup check uses an unused ID and retains its disconnected test VM. A full range skips safely. Retention defaults to preview-only; auto_delete=true additionally requires risk_confirmed=true. Both use interval_minutes and same-day UTC window_start/window_end, and require confirmed=true. Missed/overlapping runs are skipped. Disable policies before upgrades.

Restore completion, guest-agent boot response and authenticated guest readiness prove different things; none alone validates application/data recovery. Windows templates still require Sysprep and new per-clone certificate identity. Full schemas are in OpenAPI.

Dashboard backup and restore

For dashboard data recovery, see Backup & restore. The authenticated /api/dashboard-backup/export, /preview and /restore POST operations use a passphrase-encrypted file. Preview returns a review token bound to the file and destination. Portable preview reports a name conflict when same-named lab definitions differ in effective role order. Restore requires explicit confirmation. Full export and full restore also require the current administrator password. The OpenAPI document includes the request fields.

ISO library

GET /api/simple/media?node=… lists available nodes, installer candidates, driver ISOs, recommendations per OS and discovery warnings. Omit the node to use the default online destination. Guided options also include windows_label on node and mounted ISO entries. A filename match is a suggestion. To inspect one file, send node, source, os and an optional Windows agent_iso to POST /api/simple/media/verify with the selected server header. Read the returned status and detail, Linux release or Windows edition compatibility before starting a normal build review. This check never queues a job.

Portable lab packs

GET /api/simple/recipes/{id}/lab-source returns a saved build’s portable machine settings and its original steps. Pack inspection includes machines[].editable_tasks. To save a copy, author the machine with base_recipe_id or base_pack_id and base_role, then reference each desired step by its zero-based original index. It keeps its stored script body, declared inputs and destination prompts.

Use the lab pack specification to author a lab in Git or transfer it between dashboards. Version 1 creates new guests. Version 2 also supports running selected guest tasks on explicitly mapped existing machines. The Ubuntu example ZIP includes a machine, a package and a guest Ansible task.

Recipes and schedules

Recipes store a provision config without vmid or setup password, ordered task references and an optional suggested credential. Build first, finish installation, configure the guest connection, then apply tasks.

To create a schedule, POST to /api/manage/schedules with name, a reviewed plan_id, interval_minutes (15 or more), window_start/window_end (same-day UTC hours), confirmed=true and enabled=true. Schedules default disabled. Risky tasks require risk_confirmed=true. Force-stop, resize and restore cannot be scheduled. First run is at least one interval later, aligned to the next open window. Missed and overlapping occurrences are skipped. The window is checked on queuing and before each VM starts; already-running work can finish after the window closes. Saved schedule plans freeze their targets/tasks and must be reviewed again after credential rotation. List schedules for last_job/last_status and reports.

First Windows domain controller

Discover windows-domain-controller in GET /api/manage/tasks. Supply one standalone Windows Server with Desktop Experience and the built-in Administrator login. The task takes params.domain_name (forest DNS name) and params.dsrm_password (write-only recovery password). Use a single working VM build or review an existing VM in /api/simple/existing-plan, then confirm the risk and poll the job. The script installs AD DS and DNS, handles reboots, verifies the controller and places Group Policy Management and Active Directory Users and Computers on the public desktop.

Routes

GET /api/state, GET /api/jobs, GET /api/jobs/{id}, POST /api/jobs. Public liveness: GET /api/health. Browser login uses a session cookie and CSRF token; automation should use bearer authentication.

Deployment boundary

This is a single-administrator service with powerful Proxmox access. Use a trusted LAN and HTTPS reverse proxy when sharing it. Ansible can execute arbitrary code inside the container and against configured targets. Do not give access to untrusted users.

For library scripts with stored source, the existing-guest review includes the reviewed text in tasks[].source. One-off source remains in the submitted draft.

# Proxmate architecture audit

21 November 2026. Baseline revision `fba1797`. This assessment covers the first-party module inventory and dependency relationships. The detailed inspection followed guided builds, existing-machine operations, job recovery, server replacement and dashboard polling through their callers and tests. Generated editor assets, third-party implementations and individual CSS declarations were outside the detailed review.

## How the application fits together

| Responsibility | Entry points and dependencies | Where the side effects happen |
| --- | --- | --- |
| Dashboard and API | `static/index.html` loads classic scripts in order. `static/app.js` handles requests, navigation and polling. `static/simple.js` drives Create, `static/guest-operations.js` handles existing-guest tasks and `static/machine.js` handles inventory and machine actions. The editor uses CodeMirror via esbuild. Flask routes are in `app.py` and the feature modules' `register` functions. | Browsers use a session and CSRF token. API clients can use a bearer token. Host-bound writes check the selected server. The public API contract and agent examples live in `static/openapi.json` and `static/llms.txt`. |
| Guided provisioning | `SimpleFlow.plan` resolves placement, inputs, media, guest settings and frozen tasks. `Reviews.submit` can run the review off the HTTP thread. `SimpleFlow.enqueue` confirms the plan and reserves destinations. `app.run_next_job` dispatches execution. | `operations.Proxmox` handles Proxmox API tickets, task polling and SSH. `media.py` reads local or remote ISO contents. | Operating-system setup | `provisioning.answer_xml`, `windows_build.py`, `windows_setup.py`, `bootstrap.py` and the bundled PowerShell handle Windows setup. `ubuntu_build.py` handles Ubuntu media inspection, keys, autoinstall, seed media and template cloning. `template_finish.py` seals a verified build. | Python generates temporary installation media. ## Invariants future changes must preserve

- A review can store a plan. Only the confirmed submission can queue its mutations. Recheck the selected host, destination reservations, reviewed source and target identity at execution. A recycled VM ID can point to somebody else's machine.
- A server replacement and a host-bound operation must never race onto different hosts. Preserve the connection lock, pins for long-running requests and transactional idle check in `ServerConnection.change`.
- After a restart, a saved readiness checkpoint may repeat its read-only probe. Never replay an interrupted mutation automatically. Publishing a verified connection, consuming its wait and advancing the job share a transaction in `app.resume_guest`.
- A recovered task targets the original machine and frozen selection. Preserve credential revisions, per-target completion, uncertainty about already-started work and single-use continuation claims.
- Keep login material out of summaries, diagnostics and reusable recipes. Retain the different checks for build ownership, reviewed hardware and guest connection binding. Preserve how past records encode each fingerprint.

## Findings and priorities

The ranking combines the consequence of a mistake, the paths affected, available tests and the size of a safe change. Both the wizard and the composition root recur in repository history. The first three follow-ups below merit separate changes.

| --- | --- | --- |
| **High, implemented.** VM identity rules lived in `lifecycle.config_identity/machine_identity`, `Manager.identity` and `machine.stable_identity`. Windows and Ubuntu imported lifecycle for these checks. `SimpleFlow.finish_build` even obtained two helpers through `windows_build`. The hashes have different field sets and are stored in existing records. | Gather the policies in `vm_config.py`. Select the named policy at the call site and preserve the historical JSON encoding. Readers can compare the contracts in one place without constructing a manager or loading Flask. | High consequence if a field or encoding changes. High confidence in this extraction. Compare pre-change literal hashes and exercise missing IDs, replacements, disk changes, configuration drift, clones and stale connections. |
| **High, follow-up 1.** Importing `app.py` creates secrets, opens the database and calls `job_queue.initialize`, which interrupts queued and running jobs. Constructing `Manager` and `Lifecycle` can advance missed schedules. This gives importing the HTTP application operational consequences. | Give the production entry point explicit ownership of restart reconciliation. Separate opening an existing service for inspection from starting its worker. This would let tools and tests obtain an application without simulating a service restart. | High risk and moderate effort. High confidence in the issue. Specify and approve startup semantics first. Test fresh and legacy databases, two imports against the same database, a genuine process restart, waiting probes, active jobs and missed schedules. Start with `tests/test_api.py` and `tests/test_guest_waits.py`. |
| **High, follow-up 2.** `SimpleFlow.plan` interleaves source selection, remote media/key reads, credential creation in the plan, per-VM settings, task freezing, persistence and the public review response. Compare frozen plans and public review responses for ISO/cloud/clone, rejected editions, stale media, defaults, credentials and multi-VM conflicts. Use `tests/test_simple_flow.py`, `test_build_followups.py` and `test_windows_workflows.py`. |
| **Medium, follow-up 3.** `operations.Proxmox()` obtains configuration from `operations.connection_provider`, installed by `app.py`. `Reviews.submit` also assumes its caller holds `server.lock` when it pins the selected server. The provider and pin lifetime are hard to establish from an isolated caller. | Pass the selected client or configuration explicitly at the next review boundary being changed. Keep a single owner for the lifetime of that review's pin. This makes the active host visible to callers and test doubles. | High consequence if the host can change during review. Moderate effort. High confidence in the hidden dependency, medium confidence in the eventual interface. High confidence in the call path, low confidence that it causes the reported sluggishness. Compare idle and active timings, status freshness and secret redaction. A stored projection would also need migration approval and legacy-record tests. |

## Implementation sequence and observable differences

1. Ran the baseline suites. Captured exact fingerprints from the existing implementations and characterized three distinct field scopes, missing identity fields and recovery rejections. Strengthened the clone workflow's assertion to cover the bundled disk script and every parameter. Exercised filtered and full history before editing the renderer.
2. Extracted the VM checks and updated callers. The isolated identity test now imports one standard-library-only module. Previously, exercising the same rules required the lifecycle, machine and management modules. Existing callers of `Manager.identity` still use the same function via its compatibility binding.
3. Removed the task compiler's dependency on the Windows planner. Reading the disk task now requires the compiler branch and the bundled PowerShell script. The planner still verifies ownership before that task is allowed to run.
4. Removed the render-time reassignment of job history and the test fixture's duplicate script manifest. Adding a dashboard script to the page now includes it in the fixture automatically.

The changes use the existing schema, saved-record formats, API responses and deployment model. A rollback can redeploy the preceding application revision when the queue is idle. It requires no data conversion.
